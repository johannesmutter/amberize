# Preserve SQLite locks during archive reopening

The release checks intermittently record `app_started` without a subsequent integrity event. Independently, a synthetic cross-process probe reproduced an actual lock defect: after opening and closing the same database through a raw file handle, a second process obtained exclusive SQLite access while the first SQLite connection remained open. SQLite documents this POSIX behavior in [its corruption guidance](https://sqlite.org/howtocorrupt.html#posix_advisory_locks_canceled_by_a_separate_thread_doing_close_). This does not prove that the observed startup timeout has the same cause, but the defect must be repaired before publishing.

Use filesystem device/inode metadata for connection identity on Unix, without opening another descriptor. Validate existing archives through SQLite and their required schema, retaining the non-creating open flags and regular-file check. Windows retains its file-handle identity because POSIX descriptor-close behavior does not apply. Keep the four-connection memory bound and shared-connection behavior for aliases.

Keeping raw identity/header descriptors indefinitely would avoid some closes but complicate eviction and still leave temporary opens unsafe. Dropping connection reuse would increase memory and would not make independent raw closes safe. Metadata identity and SQLite validation remove the unsafe operation directly.

First add a cross-process regression that holds an archive connection, checks that another process cannot obtain exclusive access, reopens the archive through `Storage::open_existing`, and repeats the exclusive-access check. It must fail on the previous implementation and pass after the repair on Linux and macOS. Retain existing invalid-file, missing-file, alias reuse, replacement and integrity tests. Then build a fresh release and require every package recovery case, the separate-user root-owned AppImage check, all 1,024 synthetic MIME hashes and full archive integrity to pass. Preserve the unpublished 0.2.5 draft as diagnostic evidence; publish a new version with the source repair.

The user has repeatedly authorized confirmed bug repairs and instructed that work continue through release. The design adds no UI or schema changes. No password, Keychain setting, live archive or production app is changed. All Rust compilation runs in hosted CI to avoid large local caches.
