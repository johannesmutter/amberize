# Preserve SQLite locks during archive reopening

The release checks intermittently record `app_started` without a subsequent integrity event. Independently, a synthetic cross-process probe reproduced an actual lock defect: after opening and closing the same database through a raw file handle, a second process obtained exclusive SQLite access while the first SQLite connection remained open. SQLite documents this POSIX behavior in [its corruption guidance](https://sqlite.org/howtocorrupt.html#posix_advisory_locks_canceled_by_a_separate_thread_doing_close_). This does not prove that the observed startup timeout has the same cause, but the defect must be repaired before publishing.

Use filesystem device/inode metadata for connection identity on Unix, without opening another descriptor. Follow symlinks with `metadata` and compare both fields. Validate existing archives through SQLite and their required schema, retaining the non-creating open flags and regular-file check. Route manual sync/reset identity checks and export DB/WAL/SHM alias checks through the same descriptor-free comparison. Windows retains its file-handle identity because POSIX descriptor-close behavior does not apply. Keep the bound of four retained cached connections and shared-connection behavior for aliases; active owners can retain additional connections.

Keeping raw identity/header descriptors indefinitely would avoid some closes but complicate eviction and still leave temporary opens unsafe. Dropping connection reuse would sacrifice reuse and would not make independent raw closes safe. Metadata identity and SQLite validation remove the unsafe operation directly.

First add a cross-process regression that holds a WAL-mode archive connection. A fresh child uses `PRAGMA locking_mode=EXCLUSIVE` and reads its schema with a 100 ms busy timeout; it must receive `DatabaseBusy` before and after reopening through `Storage::open_existing`. Bound child execution and cover metadata identity and export checks as well. The reopening regression must fail on the previous implementation and pass after the repair on Linux and macOS. Retain existing invalid-file, missing-file, alias reuse, replacement and integrity tests. Then build a fresh release and require every package recovery case, the separate-user root-owned AppImage check, all 1,024 synthetic MIME hashes and full archive integrity to pass. Preserve the unpublished 0.2.5 draft as diagnostic evidence; publish a new version with the source repair.

The user has repeatedly authorized confirmed bug repairs and instructed that work continue through release. The design adds no UI or schema changes. No password, Keychain setting, live archive or production app is changed. All Rust compilation runs in hosted CI to avoid large local caches.
