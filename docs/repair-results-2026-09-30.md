## Further performance opportunity observed in Gmail

A metadata-only read at `06:33:58Z` found 10,237 Google message locations for 8,324 distinct blobs; 1,913 blobs already occur in multiple folders. No location has a provider message ID. Source confirms that each UID makes a size-preflight request and a body request before SHA-256 deduplication. Storage deduplication is working; cross-folder transfer and parsing still repeat. This is a measured workload characteristic and optimization opportunity, not a data-loss finding.

Two concrete follow-ups are bounded batches of UID/size metadata while retaining one-body-at-a-time fetches, and capability-gated use of Gmail’s cross-folder `X-GM-MSGID`. [Google’s IMAP extensions documentation](https://developers.google.com/workspace/gmail/imap/imap-extensions) confirms that ID identifies the same message across folders. Any reuse design must define provider/account identity and raw-content invariants, preserve per-folder UID/UIDVALIDITY locations and skip/error evidence, and pass reused-ID/content-change adversarial cases before it skips body fetches. No throughput saving is estimated, and this behavior is not changed in candidate 8.

A large real Gmail import exposed a separate restoration defect: recreating the native window called `set_active_db_path` for the archive already in use, then waited behind the whole provider-sync lock.
